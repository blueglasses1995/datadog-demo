### 演習1: パフォーマンス問題の調査と解決（30分）

#### シナリオ
「ユーザーから『アプリが遅い』という報告が複数件入っています。原因を特定し、改善策を提案してください。」

#### タスク

**Phase 1: 問題の特定（10分）**

1. **現象の確認**
   ```bash
   # トラフィック生成
   python scripts/generate_traffic.py 5
   ```

2. **Datadogで調査**
   - APM → Services → backend-api
   - どのエンドポイントが遅いか？
   - P95/P99レイテンシを確認
   - エラーは発生しているか？

3. **トレース分析**
   - 遅いエンドポイントのトレースを開く
   - フレームグラフでボトルネックを特定
   - データベースクエリ？処理ロジック？外部API？

**Phase 2: 根本原因分析（10分）**

1. **Infrastructure確認**
   - CPU/メモリ使用率は正常か？
   - データベース接続数は？
   - キャッシュヒット率は？

2. **ログ相関**
   - エラーログはないか？
   - 警告ログから手がかりを探す

3. **時系列分析**
   - いつから遅くなった？
   - デプロイと相関は？
   - トラフィック増加と相関は？

**Phase 3: 改善提案（10分）**

**レポート作成:**
```markdown
## パフォーマンス問題調査レポート

### 1. 問題の特定
- エンドポイント: /api/slow
- P95レイテンシ: 2.5秒
- 正常時: 0.1秒

### 2. 根本原因
- time.sleep()による意図的な遅延
- 実環境では: N+1クエリ、非効率なアルゴリズムなど

### 3. 改善策
- [ ] クエリ最適化（EAGERローディング）
- [ ] キャッシュ追加
- [ ] 非同期処理化
- [ ] インデックス追加

### 4. 期待効果
- レイテンシ: 2.5秒 → 0.2秒
- ユーザー満足度向上
```

### 演習2: 障害シミュレーションと対応（30分）

#### シナリオ
複数の障害を同時に発生させ、優先順位をつけて対応する訓練です。

#### 障害の発生

**障害1: データベース接続エラー**
```bash
docker-compose stop postgres
```

**障害2: 高エラー率**
```bash
# エラーエンドポイントを連続呼び出し
for i in {1..50}; do curl http://localhost/api/error; done
```

**障害3: キャッシュダウン**
```bash
docker-compose stop redis
```

#### タスク

**1. 検知（5分）**
- どのアラートが発火するか？
- Datadogで異常を確認
- 影響範囲を特定

**2. トリアージ（5分）**
- 3つの障害を優先順位付け
- クリティカル度を判定
- 対応順序を決定

**3. 対応（15分)**

優先度1（Critical）:
```bash
# PostgreSQL復旧
docker-compose start postgres

# ヘルスチェック
curl http://localhost/api/users
```

優先度2（High）:
```bash
# Redis復旧
docker-compose start redis

# キャッシュ動作確認
curl http://localhost/api/users/1
```

優先度3（Medium）:
- エラーエンドポイントの調査
- 必要に応じてロールバック

**4. ポストモーテム（5分）**
```markdown
## インシデントレポート

### Timeline
- 14:00: PostgreSQL停止
- 14:01: アラート発火
- 14:02: 調査開始
- 14:05: 復旧完了

### Root Cause
- コンテナが手動停止された

### Impact
- API全体が5分間ダウン
- 影響ユーザー: 全員

### Action Items
- [ ] ヘルスチェックモニター追加
- [ ] 自動復旧スクリプト作成
- [ ] データベースの冗長化検討
```
